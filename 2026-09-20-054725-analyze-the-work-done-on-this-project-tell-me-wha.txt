  Before you run on the NVIDIA box — blockers

  Ordered. First four stop GPU path working at all.

  1. decode: nvidia is a no-op. services/ingest/src/argus/ingest/streams.py:347
  passes options["hwaccel"]="cuda" to av.open. That is an ffmpeg CLI flag, not
  an AVOption — libav drops it silently. I proved it: bogus option, 8 frames
  decoded, no error. So NVDEC never engages, and there is no probe and no
  fallback — contradicting config/staging.yaml:3 ("falls back loudly") and
  config.py:250 ("probe falls back to software"). PyAV 18 does support it
  properly: av.open(uri, hwaccel=HWAccel(device_type="cuda", 
  allow_software_fallback=True)). Also ARCHITECTURE.md:233 already says a pip
  ffmpeg build usually has no NVDEC. Check on the box first:
  uv run python -c "from av.codec.hwaccel import hwdevices_available; 
  print(hwdevices_available())"
  This Mac's wheel lists only videotoolbox. If the linux wheel has no cuda,
  NVDEC needs a custom PyAV build — M1 exit is bigger than a config flag.

  2. Container cannot find models/registry.yaml. infra/ingest.dockerfile copies
  packages services config — never models/. infra/compose.linux.yaml mounts only
  models/artifacts, sets no ARGUS_MODELS_ROOT. So models_root() raises
  ModelArtefactError for any ONNX backend. Hidden today only because staging has
  pipelines off. Fix: COPY models/registry.yaml ./models/ (or mount ../models).

  3. CUDA EP will not load in that image. onnxruntime-gpu 1.30.0 pulls no
  nvidia-* wheels (checked uv.lock) — it needs system CUDA + cuDNN. Base is
  uv:python3.12-bookworm-slim, no CUDA runtime. Needs a CUDA base image or the
  libs installed. Native uv sync --group staging on the host works if the
  driver+CUDA are there.

  4. config/staging.yaml runs no analysis. Loaded it: pipelines.enabled=False,
  door_line count 0, no face/ui/gate sections. docker compose -f 
  infra/compose.linux.yaml up proves streams only, not the canteen path. Need a
  staging analysis config with door_line, inside_sign, analysis_fps per canteen
  camera (copy from config/dev.yaml).

⏺ Two different things are both being called "data". Untangle first.

  where you are now).

  3. Rig footage tells you nothing about accuracy

  rig/synthetic/generate.py draws bright disks moving across a frame. Not
  people. Not images of people. Coloured circles. The mock detector finds bright
  circles.

  That is deliberate and it is useful — it proves RTSP, decode, tracking,
  line-crossing, clip extraction, event writes, pairing, fail-open, with ground
  truth known to the millisecond. It proves zero about whether a camera can see
  a person in a doorway.

  Point a real YOLO at rig footage and it finds nothing, because there is
  nothing there. Expected, not a bug.

  4. Recordings first — yes, and the repo is built for exactly that

  You do not have to go live on day one, and you should not. The rig is not a
  fixture, it is infrastructure: rig_common.ffmpeg_cmd serves any mp4 over RTSP
  with -c copy, looped. Drop your own recording into rig/footage/, write a
  manifest for it, and it becomes a virtual camera playing real footage. Tests
  always consume through RTSP, so replay and live are the same code path.

  tests/rig/test_canteen_replay.py is the measuring harness — it reads the
  manifest's ground_truth.crossings list and compares. Your recording gets the
  same treatment: you hand-label what actually happened, replay, count.

  So the accuracy path is: record → label → replay → measure → tune → live.
  Live-from-day-one is the thing to avoid.

  How you finish it — 7 steps

  Steps 1–5 here on the Mac, 6–7 on the box.

  # 1. get the file. Export in a THROWAWAY venv, never the project env —
  #    ADR-0030 works because no AGPL *code* enters this runtime, only weights
  python3 -m venv /tmp/ul && /tmp/ul/bin/pip install ultralytics
  /tmp/ul/bin/yolo export model=yolo26m.pt format=onnx
  mkdir -p ~/artefacts && mv yolo26m.onnx ~/artefacts/

  # 2. hash it
  shasum -a 256 ~/artefacts/yolo26m.onnx

  3. In models/registry.yaml, fill sha256:, set url: 
  file:///Users/you/artefacts/yolo26m.onnx, and delete the status: unresolved 
  line. Leave commercial_use: false. The recipe is written in the file itself
  now.

  # 4. fetch + verify (a file:// url keeps the hash check in the loop)
  uv run python models/fetch.py

  # 5. produce and commit the reference — CPU, on this machine
  ARGUS_MODELS_ROOT=models uv run python tests/golden/make_reference.py yolo26m
  ARGUS_PARITY_ARTEFACT=yolo26m ARGUS_PARITY_BACKEND=onnx-cpu-yolo uv run pytest
  -m golden -q
  git add models/registry.yaml tests/golden/reference/yolo26m.json

  Then scp the .onnx to the box (or host it where the box can fetch it — the
  hash makes the transport irrelevant), and there:

  # 6. the CUDA leg against your committed CPU reference — the number that 
  matters
  ARGUS_MODELS_ROOT="$PWD/models" ARGUS_PARITY_ARTEFACT=yolo26m \
    ARGUS_PARITY_BACKEND=onnx-cuda-yolo uv run pytest -m golden -q

  # 7. only then point a pipeline at it
  #    config: pipelines.detector_backend: onnx-cuda-yolo
